PostgreSQL STIG Compliance Artifact

Control Identification

Control ID: V-206521
Title: Enforce Least Privilege Access to Database Objects
Severity: CAT I
System: PostgreSQL 15 / 16 on Red Hat Enterprise Linux 8
Compliance Status: COMPLIANT

⸻

1. Control Requirement

The DBMS must be configured so that users are permitted access only to objects and data they are authorized to view or interact with, and prevented from accessing all other objects and data.

This requirement enforces the principle of least privilege and prevents unauthorized data exposure or modification.

⸻

2. Control Objective

The system must ensure:

• Users are granted only the privileges required for their role
• PUBLIC schema access is restricted
• Default privileges are hardened
• Object-level permissions are explicitly defined
• Superuser privileges are limited
• Unauthorized data access is prevented

⸻

3. Implementation Summary

Requirement	Implementation
Restrict PUBLIC privileges	REVOKE ALL FROM PUBLIC
Enforce schema ownership controls	Explicit schema ownership
Default privilege control	ALTER DEFAULT PRIVILEGES
Role-based access model	Application roles defined
Limit superuser usage	Only postgres is SUPERUSER
Prevent cross-schema access	Explicit GRANT model
Audit privilege changes	pgaudit enabled


⸻

4. Technical Implementation Details

⸻

4.1 Revoke Default PUBLIC Privileges

By default, PostgreSQL grants some access to PUBLIC. These privileges are removed.

REVOKE ALL ON SCHEMA public FROM PUBLIC;
REVOKE ALL ON DATABASE <dbname> FROM PUBLIC;

Verification

SELECT nspname, nspacl
FROM pg_namespace
WHERE nspname = 'public';

Expected Result:
No permissive PUBLIC privileges.

⸻

4.2 Implement Role-Based Access Control (RBAC)

Roles are defined by function:

• app_readonly
• app_readwrite
• dba_role

Example implementation:

CREATE ROLE app_readonly;

GRANT CONNECT ON DATABASE mydb TO app_readonly;
GRANT USAGE ON SCHEMA app TO app_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA app TO app_readonly;

Users are assigned to roles:

GRANT app_readonly TO user1;


⸻

4.3 Control Default Privileges

Ensure new objects do not inherit open access.

ALTER DEFAULT PRIVILEGES IN SCHEMA app
REVOKE ALL ON TABLES FROM PUBLIC;

Controlled privilege grants:

ALTER DEFAULT PRIVILEGES IN SCHEMA app
GRANT SELECT ON TABLES TO app_readonly;


⸻

4.4 Restrict Superuser Privileges

Verification

SELECT rolname
FROM pg_roles
WHERE rolsuper = true;

Expected Result:

postgres

No application accounts have SUPERUSER privilege.

⸻

4.5 Restrict Cross-Schema Access

Users have:

• USAGE only on required schemas
• Object-level grants for required tables
• No blanket database-wide permissions

Verification

SELECT grantee, privilege_type
FROM information_schema.role_table_grants
WHERE grantee = '<username>';


⸻

4.6 Enable Audit Logging of Privilege Changes

PostgreSQL configuration:

shared_preload_libraries = 'pgaudit'
pgaudit.log = 'role, ddl'

This logs:

• GRANT
• REVOKE
• Role changes
• Schema changes

⸻

5. Administrative Procedures

The organization maintains a documented procedure titled:

PostgreSQL Role and Privilege Management Policy

The procedure includes:
	1.	All access must be role-based
	2.	Direct object grants to users are prohibited
	3.	PUBLIC privileges are revoked
	4.	Superuser access restricted to DBA team
	5.	Privilege changes require change management approval
	6.	Quarterly privilege review required
	7.	Application roles reviewed during release cycles

Document Location

/security/sops/postgresql_access_control_policy.docx

8. Risk Analysis

Without proper object-level controls:

• Unauthorized data exposure could occur
• Lateral privilege escalation risk
• Data integrity compromise
• Regulatory violations

Mitigations implemented:

• Least privilege enforced
• PUBLIC access removed
• Explicit GRANT model
• Audit logging enabled
• Regular access review

Residual Risk: Low

Final Statement

PostgreSQL is configured using a role-based access control model that restricts users to authorized database objects and prevents access to all other objects and data.

Default PUBLIC privileges are revoked, superuser access is restricted, and privilege changes are audited.

The system satisfies the requirements of STIG V-206521.
